# 会话归属与接续（Contract C13）

一台设备开的会话，别的设备能接着聊，并且接着的是**原来那份完整上下文**——不是
同步过来的一段文字。这一页是这件事的设计：什么算「归属」、一句话交给谁跑、逐字
输出怎么让所有设备都看到、插话怎么落到正在跑的那一轮里。

> 与 [sync.md](sync.md) 的 C12 区分：C12 说的是**会话属于哪个账号**（family
> tablet、换账号、退出登录时的可见性）；C13 说的是**会话由哪台设备持有**（谁有那份
> 完整上下文、谁跑这一轮）。同一台设备上，一个会话同时有一个账号 owner 和一个设备
> owner，两者互不影响。

## 一、为什么需要它

nanoMuse 的每一台设备各自持有自己的 LLM 上下文：完整历史（含工具调用轨迹、图片、
推理）落在该设备本地的 `{data_dir}/threads/{id}.session.json`，中继只同步
**user 与最终 assistant 的纯文本**（`nanomuse/sync/engine.py` 的 wire 只有
`mid/cid/role/text/created_at/attachments`）。因此在一台设备上看着另一台同步过来的
会话，只能看到文字，模型的记忆接不上，也无法把话交给那台设备在**那条会话**上执行。

C13 的做法：**每个会话有一个归属设备（owner device）**，完整上下文永远只在它本地，
别的设备发消息时请它**代跑这一轮**；它的逐字输出由中继广播给同账号的所有在线设备。
上下文不搬家，所以永远接得上。

## 二、归属规则

- **每个会话有一个 owner device。** 主会话与每一个设备专属会话都有；值一律是
  **`device_id`**，不是名字（改名不失效——`rename` 帧只改 `name`，见
  `cloud/nanomuse_cloud/hub.py`）。
- **默认发给 owner。** 在当前会话里不写 `@`，这一句就交给 owner 跑。
- **`@` 显式切换，且黏住。** 写 `@<设备名>` 就把这条会话的 owner 换成它，之后不写
  `@` 也继续发给它；写 `@本机`（本机名亦可）换回本机。归属看的是「这条会话属于谁」，
  **不是「上一条消息从哪来」**——owner 那边同步过来的一轮结束了，下次不写 `@` 仍然
  发给 owner。
- **`@` 优先于归属。** 一句话开头写了别的设备名，就去那台，无论当前 owner 是谁。
- **本机出口必须存在。** `@` 的匹配现在主动排除自己（`nanomuse/sync/mention.py` 的
  `self_id`），中继也硬拒自己调自己（`cloud/nanomuse_cloud/hub.py` 的 `self_call`），
  合起来等于「本机永远不能当目标」。C13 加一个特例：**`@本机`、本机设备名都算作
  「这一句在本机跑」**，把 owner 切回本机。
- **切 owner 就是换记忆。** `@本机` 之后本机用**自己那份**上下文，**没有原 owner 的
  工具轨迹**。切换时在会话里落一条说明（谁从谁手里接手），让模型知道上下文有断层。
- **界面必须常显当前 owner。** 输入框上方固定一行（如「由 飞牛深圳 执行」），切 owner
  时随之变化。

### 一句话的路由顺序

1. 开头 `@` 了某台设备（含本机）→ 这一句给那台，并把 owner 改成它。
2. 否则 → 给当前 owner。
3. owner 就是本机 → 走原来的本地路径（行为与今天一致）。

## 三、代跑一轮

发起端把这一句交给 owner，owner 在**它自己那条既有会话**上跑一轮，并把这一轮的
逐字输出回传。要点：

- **同一份上下文，不复制。** owner 打开的是它自己那条会话（主会话就是 `main`），
  不是新建的 `From <device>` 会话。
- **单次推送（单 mid）。** 一句话只有一个 `mid`：发起端推的那条就是权威，owner 回传
  的 user 行必须**复用同一个 `mid`**，owner 不得再为同一轮另起 `mid` 上推。否则中继
  按 `mid` 去重挡不住，同一句会在所有设备显示两次，两边模型的上下文里也各出现一次。
- **「谁问的」走侧信道。** 由谁发起、在哪台执行，不能拼进用户消息正文（DSH 的
  `[Asked from …]`、Android/iOS 的 prefix 都是这个做法，会永久污染对方会话的历史）。
  用 Python runtime 已有的 `purposes` 那样的并行通道，或一条独立的 system 行。
- **代跑标记与同步解耦。** `sync/engine.py` 的 `_eligible()` 会把
  `thread.remote_from` 的会话**排除同步**。给「这条线程整体属于某台设备」
  （`remote_from`）与「这一轮由某台设备代跑」用**两个不同的标记**；后者必须仍然同步。
- **跨端互斥。** 同一会话同一时刻只有一个驱动者。owner 本地正在跑（或已被别的设备
  代跑）时，新的代跑请求**明确拒绝**（提示「<设备> 正在忙」），绝不把消息折进正在跑
  的那一轮（`nanomuse/agent/core.py` 的 `_drain_inbox` 会那样做，这里不能走那条路）。
- **owner 离线不发。** owner 不在线时**不把消息上屏**，直接提示「<设备> 离线，未发送」。
  不留「已发送却永远没人跑」的状态。
- **附件**：阶段一明确不支持跨设备携带文件；带文件时**发不出去并说明原因**，不做
  静默失败（现有 task args 只有 text，同步 wire 只有 `{name,mime,size}`）。

## 四、流式同步

owner 跑这一轮时，逐字文本、推理增量、工具调用与结果都要让同账号的在线设备看到。

- **通道**：中继新增一种服务端构造的帧（暂名 `stream`）与一个上行端点（暂名
  `POST /v1/sync/stream`），沿用 `working` / `sync` 已有的「遍历
  `online[account_id]` 逐个 send」的扇出写法。
- **合批**：帧量必须压。逐字 + 推理 + 工具过程一条帧一个字会撞
  `FRAMES_PER_S=60` 与 `SEND_QUEUE_FRAMES=512`；按 200–250ms 合并一批再发。
- **来源标识**：帧里必须带「哪个会话、谁在说、第几轮」。Web 端现在按会话键
  （`state.streams[thread]`）存正在生成的文字，两股流会互相覆盖；没有来源标识就没法
  正确渲染。
- **权限**：沿用现有模型——中继只把帧发给同账号的在线 socket，且（若涉及审批）
  只发给声明了相应能力的设备。旧客户端不认识新帧时**静默忽略**（Android 的 `when`
  无 else 分支、TS 的 `switch` 有 `default: return`），服务端收到未知帧回 `bad_frame`
  且**保持连接**——所以三端可以逐个升级。
- **能力协商**：新能力加入 `welcome.server.features`（现有值为 `event_push`）。注意
  现有机制只是「服务端单向声明 + 客户端据此决定是否发送」，**没有**「服务端按客户端
  版本降级行为」的能力；需要降级时要另外记录客户端声明。
- **断线**：中继的转发即发即丢、无重放，中间流允许断；**最终文本由 sync 兜底**，
  重连后以 pull 到的最终答案为准。

## 五、插话与排队

代码里**已经有轮内插话**：`nanomuse/agent/core.py` 的 `_drain_inbox()` 挂在**每一步**
（step）循环的开头，`thread.agent.inbox = thread.inbox` 把线程队列直接交给 agent。
模型每走一步都回头看队列，来了新话就从下一步按新的走——这与 Codex 的 steer 同构。

因此做成两级（对照 Codex：Enter 插话 / Tab 排队）：

- **插话纠偏（默认）**：话立刻上屏（所有设备可见），**当前这一步的工具跑完就生效**，
  不等整轮结束。用来改方向、补条件。
- **排队**：等这一轮**整个**结束再作为下一轮开始。
- **多端插话要能投进去**：别的设备插的话必须能塞进 owner 那条**正在跑的**队列。这需要
  中继加一条反向的「插话投递」路径（发起端 → 中继 → owner → `thread.inbox`）。owner
  侧不用改，它本来就在每步查队列。
- **不做硬打断作为默认**：`worker.cancel()` 会在模型刚问过问题或刚发起工具调用时留下
  「问了没人答」的残局，多端同步时那条坏记录所有设备都看得到。硬打断仅作兜底，且触发
  时自动补一句收尾。
- **顺序**：中继按会话维护顺序，谁的话都进同一个队列，先到先算。

## 六、暂不做

- 跨设备携带文件（阶段一直接拒绝并说明）。
- 记忆 / 目标 / 提醒的跨设备一致：它们在各设备本地 SQLite（`nanomuse/server/service.py`
  的 `data_export_sources`），代跑用的是 owner 的记忆，不迁移。
- 非发起设备接收审批卡：现有链路只把卡给 call 的发起端；旁观端收不到。审批卡的回传
  在后续阶段单独做。
- iOS：本契约先落 Mac + Web + Android，iPhone 随后跟进（新帧对旧端是静默忽略，不会坏）。

## 八、专属会话：一轮跨设备对话画在哪

一轮代跑跑在 **owner 自己那条 main 会话**上，所以中继把这一轮记在**账号共享的 main
cid** 下。而每台设备本地都有一条「和这台设备的会话」（`DeviceChat` / `deviceChats` /
`hub.session.to-<hubId>`），点设备头像进的就是它。

于是同一个回合有两个合理的落点：中继给的会话，和设备自己的会话。原先只落前者，
后者空着，但人是在后者里看这台设备干活的。

**决定：两处都落。** 一轮从 device X 来的回合，除了写进中继指的那条会话，**再往
「和 X 的会话」写一份**：

- **同一 `mid`，两份行。** 中继的主键是 `(account_id, mid)`，一份记录只能有一个
  `mid`；本地两行靠各自的 `messageId` 区分，共用 `mid`。删除到达时按 `mid` 查全部
  副本一并移除（Android `messagesByMid` / Mac `state.mirrored`）。
- **只在「已经有这条会话」时镜像。** 人没点开过的设备，不主动造一条会话出来。
- **流式同规则。** `stream` 帧的 `cid` 指中继那条会话，所以按 `cid` 只能画进主会话。
  渲染时**再按 `from`（跑这一轮的设备 id）匹配一次**，那条会话也画（Android
  `streamsFor` / Mac `stream-view.ts` 的 `deviceOf`）。中继不重复扇出。
- **一句话一个 `mid`。** 发起端在自己那条行上派生 `mid`（Android `HandoffMid`，
  对齐 Mac `deriveMid`），随 `task` 帧给 owner；owner 用它写自己的行。谁先推，中继
  都只留一行；发起端本地那一行登记为已推，不再推第二遍。
- **主会话照旧。** 镜像不是搬迁：中继那条会话仍然收到这一轮，行为与从前一致。

不做的是「专属会话各自一个 cid」：中继的 `main` cid 全账号唯一，一条 main 只能映
射给一条本地会话，两处都要就得两套 id，会把归属与代跑整体推翻。
